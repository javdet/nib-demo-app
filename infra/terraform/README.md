# Infrastructure

Terraform for the production stack described in the root README's *Deploying to AWS* section:
CloudFront + S3 for the SPA, an ALB in front of ECS Fargate for the API, RDS Postgres behind
that. One environment (`production`), one region (`us-east-1`), applied by GitHub Actions - not
from a laptop.

- **Terraform** `1.10.5`
- **Provider** `hashicorp/aws` `5.100.0`, `hashicorp/random` `3.7.2` - see `.terraform.lock.hcl`
  for the checksums; it is committed deliberately (see `.gitignore`) so `terraform init` is
  reproducible in CI.

## Backend

`versions.tf` declares a *partial* S3 backend - `region`, `encrypt` and `use_lockfile` are fixed
in the file, but `bucket` and `key` are supplied at `terraform init` time, because the bucket name
is derived from the AWS account id and backend blocks cannot reference variables:

```
bucket = nib-demo-terraform-state-${AWS_ACCOUNT_ID}
key    = nib-demo/prod/terraform.tfstate
region = us-east-1
```

`deploy-infrastructure.yml` derives `AWS_ACCOUNT_ID` from `aws sts get-caller-identity` and passes
both as `-backend-config` flags. State locking is S3's native conditional-write locking
(`use_lockfile = true`, Terraform 1.10+) - no DynamoDB table to provision or pay for.

The state bucket itself is **not** managed by this configuration - it has to exist before
`terraform init` can run against it. Create it once, by hand or with a separate bootstrap, with
versioning and encryption enabled.

## Topology

```
Internet -> CloudFront -----> S3 (private, OAC)         SPA + static assets
                 \
                  \--/api/*--> ALB -> ECS Fargate (api) -> RDS Postgres (Multi-AZ)
                                       private subnets      isolated subnets
```

- **Network** (`network.tf`) - one VPC across two Availability Zones, three subnet tiers: public
  (ALB + one NAT gateway per AZ), private (ECS tasks, each routed to its own AZ's NAT so one NAT
  or AZ failing doesn't take down both), and database (RDS, no route to the internet at all).
- **Security** (`security.tf`) - the ALB accepts port 80 only from AWS's
  `com.amazonaws.global.cloudfront.origin-facing` managed prefix list (CloudFront's edge ranges,
  not the public internet); ECS accepts 8000 only from the ALB's security group; RDS accepts 5432
  only from ECS's security group and has no egress rule at all.
- **ECR** (`ecr.tf`) - one immutable, scan-on-push repository, `nib-demo-prod-api`.
- **Database** (`database.tf`) - Multi-AZ RDS Postgres, engine version `16`, database `nibshop`,
  user `nibapp`, a `postgres16` parameter group with `rds.force_ssl = 1`, GP3 storage with
  autoscaling, encrypted at rest, deletion protection on. The master password is generated by the
  `random` provider and is **never** a Terraform output - it exists only inside RDS and inside the
  Secrets Manager secret below.
- **Secrets** (`secrets.tf`) - logical contract URI `aws-secretsmanager:nib-demo/prod/database`
  maps to the real secret name `nib-demo/prod/database`. It holds the individual connection
  fields (host, port, dbname, username, password) plus a ready-to-use, URL-encoded `DATABASE_URL`.
  A resource policy grants read access to the ECS execution role only.
- **ALB** (`alb.tf`) - internet-facing, one IP-type target group on port 8000, health check at
  `/api/health/ready`, one plain-HTTP listener. It is never addressed directly by a client; it
  exists to be CloudFront's `/api/*` origin, and the security group is what actually enforces that.
- **ECS** (`ecs.tf`) - cluster `nib-demo-prod` with Container Insights, a 30-day log group, a task
  execution role scoped to image pulls, log writes and the one database secret, and a task role
  with no permissions at all (the application only ever talks to Postgres). Fargate platform
  `1.4.0`, task family and service both named `nib-demo-prod-api`.
- **Static site** (`static-site.tf`) - private, versioned, encrypted bucket
  `nib-demo-prod-web-${AWS_ACCOUNT_ID}`, all four public-access-block settings on, bucket-owner-
  enforced ownership (no ACLs - CloudFront reads it through an Origin Access Control instead).
- **CloudFront** (`cloudfront.tf`) - one distribution, two origins: the S3 bucket (default, via
  OAC) and the ALB (`/api/*`). Viewers are redirected to HTTPS. The API behavior disables caching
  entirely and forwards every method, query string, cookie and required header (`Managed-
  CachingDisabled` + `Managed-AllViewer`); the default behavior uses `Managed-CachingOptimized`
  and `Managed-SecurityHeadersPolicy`. S3's `403`/`404` responses (a client-side route that isn't a
  real object) are rewritten to `/index.html` with a `200`, so deep links survive a hard refresh.
  The bucket policy authorizes reads from this one distribution's ARN and nothing else.

## The ECS bootstrap

`terraform apply` cannot publish a container image - that's `deploy-application`'s job - so
`aws_ecs_service.api` is created at **desired count 0**, pointed at a task definition whose image
is `<ecr_repository_url>:bootstrap`, a tag nothing ever pushes. Because desired count is 0, ECS
never tries to pull it. The service has:

```hcl
lifecycle {
  ignore_changes = [task_definition, desired_count]
}
```

so that once `deploy-application` registers a real task-definition revision and scales the service
to its steady count (2), a later `terraform apply` does not see that as drift and revert it. Run
`Deploy Infrastructure` before the first `Deploy Application` run; running it again afterwards is
safe and a no-op on those two fields.

## Cost

This is a demo, but two things in it cost money whether or not anyone is using the site:

- **Multi-AZ RDS** roughly doubles the instance cost of the database over a single-AZ instance.
- **Two NAT gateways** (one per AZ, for ECS's outbound access) bill hourly plus per-GB processed,
  independent of traffic.

Both are deliberate - they're part of what the `/deployment` page is demonstrating - but they are
not free, and `terraform destroy` does not fully undo the RDS side of that: see below.

## Destructive operations

- **RDS** has `deletion_protection = true` and `skip_final_snapshot = false`. A `terraform
  destroy` fails until protection is turned off, and even then leaves a final snapshot
  (`nib-demo-prod-postgres-final`) behind - which itself costs storage until someone deletes it by
  hand.
- **The Secrets Manager secret** is created with a 30-day recovery window, not immediate deletion;
  a destroy/recreate leaves the old secret recoverable (and its name reserved) for 30 days.
- **The web bucket** is not force-emptied by Terraform. A bucket that still has objects (including
  old versions - it's versioned) will fail to delete; empty it first if a destroy is intended.
- **ECR** images are not force-deleted by Terraform either; a non-empty, immutable-tag repository
  will similarly refuse to delete.

None of this happens as a side effect of `terraform apply` - it only matters if someone runs
`terraform destroy` against this state, which is not part of either workflow.

## Workflow order

1. **`Deploy Infrastructure`** (`.github/workflows/deploy-infrastructure.yml`) - `terraform plan`
   on every push/PR touching `infra/terraform/**`; `terraform apply` only from an explicit
   `workflow_dispatch` with `apply: true`, gated by the `production` environment's required
   reviewers.
2. **`Deploy Application`** (`.github/workflows/deploy-application.yml`) - reads this
   configuration's outputs (`terraform output -json`, same backend, same state - no separate
   copy of any resource id), builds and pushes the backend image, registers a new task-definition
   revision, updates the service to the steady desired count, builds and syncs the frontend, and
   invalidates CloudFront.

Run 1 before 2 ever, and after any change to `infra/terraform/**`. Run 2 on its own for a plain
application deploy - it does not touch Terraform state.

The binary plan `terraform-plan` uploads and `terraform-apply` later downloads is a GitHub Actions
artifact scoped to this repository, but a Terraform plan file is not redacted the way CLI plan
output is - it can contain sensitive values (the generated database password among them) in the
clear. Treat that artifact, and who has read access to this repository's Actions runs, accordingly.

## Variables

See `variables.tf` for the full list and their `validation` blocks, and `terraform.tfvars.example`
for a working copy of the defaults. A handful of them - `aws_region`, `environment`,
`db_engine_version`, `db_name`, `db_username` - are validated to equal one specific value: they
are not independently configurable because the application, the migrations or the rest of this
configuration are written against that exact value.
